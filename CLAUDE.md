# Lendo — rules for working in this repo

- Cloudflare Workers + Hono + TypeScript, server-rendered Hono JSX. No framework migration without asking.
- Data: D1 via `c.env.DB.prepare(...).bind(...)` with parameters — never string-interpolate user input into SQL. Schema changes = new file in `migrations/` (never edit an applied migration).
- Photos: R2 only; keys `listingId/…` and `rentals/rentalId/…`. Serve via `/p/:key`.
- Auth: phone + texted code, session cookie `lendo_s`. Every route that reads or changes a user's data must check ownership (`owner_id === u.id` / party of rental). `requireUser` only checks login, not ownership.
- Money: all amounts in integer cents. Customer pays rent − credit + sales tax (NYC 8.875%, Iowa City 7%; `src/lib/money.ts`). Fee = 15% × (rent + tax), taken from the owner: owner gets rent − fee (`payout_cents`; old rows without it: rent). Lendo absorbs credits and remits tax. Stripe flow is hold → capture on YES → release on NO/expire. Deposit hold (Scott, 11/24): every rental, for the item's value, set by AI not the owner (`listings.value_cents`, `src/lib/value.ts`; valued at the first request, owner can ask early or appeal once on the edit page) → `rentals.deposit_cents` at request, card saved at every checkout, hold placed on pickup day (owner sees "OK to hand over"), renewed every 6 days while out or while a claim is open, released when the owner taps "All good" or 24h after return (`rentals.ts` allGood/holdDeposit/depositsDue), captured only by a final AI ruling. Problems (`src/lib/claims.ts`, `/r/:id/claim`): owner claim → customer response → owner reply → customer last word (24h each) → AI ruling → both OK or one second look → final → `collectAward` from the hold + `payClaim` to the owner (no fee). Bank disputes: `onDispute` puts the evidence file on the Stripe dispute; Lendo covers the owner up to `settings.guarantee_cap_cents` (`/admin/claims`). The judge prompt (`RULES` in claims.ts) is policy: change it only when Scott asks. Changes to `src/lib/stripe.ts` or `src/lib/rentals.ts` need a second review pass for state-machine and refund correctness.
- Logging: every state change, money movement, webhook, login, listing change, admin action and error goes to the `events` table via `logEvent`/`logErr` (`src/lib/log.ts`); never delete rows from it. Admin views: `/admin` (dashboard, log, rentals, users, texts, searches, errors, CSV). Admin access: owner = `ADMIN_PHONES`; owner grants `view` (GET only) or `full` (all but /admin/access) at `/admin/access` (`users.admin_role`).
- Texts: all outbound texts go through `textUser` (logs to `outbound_texts`, respects STOP and `users.sms_ok`). Keywords handled in `src/routes/webhooks.ts`. Texting is primary; email (`src/lib/email.ts`, Resend) is the backup, never both unless a text got no response — except rental requests to the owner, which are always emailed at the same time as the text (`emailRequest`, Scott 11/24). Emails: no box/card, fluid ≤480px, same timeline-rail steps as the rental page. Dates are numeric everywhere ("Sat 11/28", `fmtDay`). Rules (Scott, 11/24): the user texts first (login page leads with "Text OK to Lendo", code form below as backup); each person has an allowance of texts in a row (`textAllowance`: Blooio tiers 3/4/6/8, Linq 6) that a written reply or a tapback resets (`recordTap`); decisions say "reply YES or NO", other texts ask for a 👍 only on the last allowed text (`KEEP_ASK`); past the allowance, rental/money/pickup/chat texts go by SMS line or email right away, nudges/alerts just wait in the web inbox; an unanswered request is emailed after 15 min (pickup today/tomorrow) or 2h (`src/lib/escalate.ts`). Phone buttons for YES/NO/I'm here are `sms:` links (`smsHref`, YES/NO carry the rental's last 4 chars). Email is required, asked on the welcome screen (`users.email`).
- Copy voice: platform/tool voice — functional, not personified, no "we're so excited". No trailing periods in texts/UI lines (occasional "!" ok). Persuasive but not crass: mix community + money, don't lead with money. Name the neighborhood ("12 Northside neighbors…"); "neighbors" fine, never a vague "your neighbors". Now and then invite spreading it ("got one, or know someone who might?"). Never "gathering dust"-style cutesy lines.
- Terms: "owner" (lists, gets paid) and "customer" (rents, pays). Never "renter" in copy or new code names. Customers "rent", owners "list". Fee is "15% fee (will stay low)", paid by the owner out of the rent, charged from day one; customers never see a fee line; a free rental (owner waived) has no fee or tax.
- Design minimal (Scott, 11/23): no dotted/dashed borders, no decorative number badges or alternating filled/outline styles, plain labels (e.g. "Condition", not "What shape is it in?")
- Brand: cream `#F5F3EE`, ink `#1E3A2B`, orange `#FF4F00`, Helvetica Neue; 👋 Lendo logo. Tokens in `public/app.css`. Design is always chunky, easy, simple, minimal: chunky icons (stroke ≥3, round caps, shared in `src/lib/icons.ts`), never thin glyphs/arrows.
- Verify: `npm run typecheck`, then `npm run dev` + walk the flow (list → rent → YES via `/webhooks/blooio` → pickup → return → rate).
- Item names/descriptions: name the brand (+ model) when visible AND it matters to a customer (electronics, cameras, power tools, appliances, audio, bikes, fitness, baby gear, designer fashion, outdoor brands); leave it out for commodity items (folding chairs, ladders, hammers, sleds). Never guess a brand. Descriptions = 1-2 lines of checkable facts (model, key spec, what's included, visible condition), no filler. Rules live in `src/lib/identify.ts`.
